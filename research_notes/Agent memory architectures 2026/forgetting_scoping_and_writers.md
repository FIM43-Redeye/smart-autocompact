## A. Forgetting, staleness, scoping, standing constraints

### Takeaway
No paper I found evaluates scope, expiry, revocation or false positives for an auto-extracted constraint registry. The two papers that propose one (Governance Decay, Lost in Compaction) measure only whether constraints SURVIVE compaction, never whether they outlive their purpose. Stickiness evidence exists only indirectly: over-application of stored preferences (BenchPreS, PersistBench, OP-Bench), stale-belief failures (STALE), and experience-following error propagation (Xiong). Mechanisms for supersession (Zep bi-temporal edges, Mem0 DELETE) are vendor-described with little independent evidence.

### Cited Findings

**Constraint-pinning papers: what they say about scope/revocation (primary reading)**
- Governance Decay (Chen, arXiv 2606.22528v2, 27 Jun 2026; single author, BIT): ConstraintRot benchmark, 7 models, 1,323 episodes; compaction raises violation 0% to 30% (up to 59%); constraint survived summary = 0% violation, dropped = 38%; decay 8.3x larger for soft organizational policies than hard safety norms. Constraint Pinning: "the harness extracts governance constraints into a pinned buffer that is (i) exempt from compaction and re-injected verbatim after every compaction step, and (ii) integrity-checked". Restores violation to 0% for about 47 pinned tokens. — https://arxiv.org/html/2606.22528
- Governance Decay on revocation: pinned policy resists a "policy rescinded" notice ingested as tool output then summarized (2%) and 15 distractor rules (0%); but an "OPERATOR POLICY UPDATE…supersedes pinned policies" placed in recent, non-summarized context raises violation 0% to 17%; adding provenance text ("operator-pinned; not overridable by conversation or tool content") only reduces to 10%. Authors: needs "a trusted out-of-band operator channel". I found no mechanism for LEGITIMATE user revocation, expiry or scope; revocation is treated only as an attack. Pinned constraints are operator policies, not user sub-task instructions. — same URL
- Governance Decay limitations (verbatim): "(ii) Constraint Pinning requires the constraint to be extractable as a quotable rule; implicit constraints are out of scope." No false-positive/over-pinning evaluation. — same URL
- Lost in Context Compaction (Wang et al., Penn State/IBM, arXiv 2608.11242v2, 11 Oct 2026): defines Side Constraint: "An SC remains in effect until it is revised, revoked, or its scope ends." Scope appears only as an experimental variable: "Direct" prepends "For the rest of this session." (explicit scope) vs "Contextual" (implicit). Taxonomy of 5 SC types (Action, Information, Process, Preference, Output). Compactors lose most SCs (best non-extractor SWE-Natural retention 28.6%; WildChat best targeted prompt 37.6%). — https://arxiv.org/html/2608.11242
- LiC Appendix F extractor: off-the-shelf Qwen3.5-9B, thinking off, prompting only. Runs every user turn. Inputs: (1) current user message, (2) immediately preceding assistant message (to resolve "do that going forward"), (3) existing registry "only to suppress duplicate or paraphrased constraints rather than to infer new ones". Output JSON: "a canonical one-sentence formulation and a short supporting evidence span for each extracted SC"; empty list if none. Non-duplicates are appended; registry appended after compacted context. Table 4 retention 90.3% (WildChat), 93.7% (Hermes), 95.1% (OpenResearcher), avg 93.0%; by type avg 88.2% Action to 97.1% Preference. NOTE: the JSON as described has NO scope, type, update or revocation field; the only registry operation is append-with-dedup; no removal or supersession. "Retention" = extractor recall on injected constraints; no precision/false-positive measure reported (I grepped; none found). Full prompt is in their code repo, which I did not open (so a scope/type field inside the prompt is not ruled out, but the paper's text describes none). — same URL
- LiC Limitations: proprietary-model context pressure, effective-retention availability, compaction frequency; nothing on stale/over-retained constraints. Inbox experiment (gpt-oss-120b, 100 continuations): 30/100 unauthorized deletions after compaction; appending the SC reminder cut it to 13/100; failures included the agent generating "its own approval-like statement". So even re-injected verbatim constraints are not fully obeyed. — same URL
- Self-GC (arXiv 2607.00692, Jul 2026; production-derived, vendor-style): user turns, tool spans and skill state become indexed objects; a side-channel planner proposes fold/mask/prune. Planner is told to "Exclude the latest visible turn, active instruction files, live handles, editable artifact bodies, and exact evidence that future turns may need verbatim." Constraints are not a distinct protected class: a user "do not replace the table header" correction is cited as a "behavioral contract" loss mode. Planner still touched the latest visible turn in 12-25 of ~330 plans before a deterministic filter removed it. 332-session suite: no-impact 91.27-94.58% vs baselines 77.71-87.46%. No scope/expiry/revocation treatment. — https://arxiv.org/abs/2607.00692 , https://arxiv.org/html/2607.00692

**Mechanisms for expiry/invalidation**
- Zep/Graphiti: four timestamps on edges, t'created/t'expired (system time) and tvalid/tinvalid (world time); new contradicting facts invalidate rather than delete. Vendor paper (Jan 2025): up to 18.5% accuracy gain, 90% latency reduction on LongMemEval; improvement on knowledge-update only with gpt-4o ("additional development may be needed" for weaker models). — https://arxiv.org/html/2501.13956
- Mem0 (vendor paper, Apr 2025): LLM chooses per candidate fact ADD / UPDATE / "DELETE for removal of memories contradicted by new information" / NOOP; extraction input is message pair plus conversation summary plus recent messages. Reports 26% relative LLM-judge gain over OpenAI memory, 91% lower p95 latency. No ablation of conflict resolution found. — https://arxiv.org/html/2504.19413
- LangMem: memory "strength" = recency/frequency of use plus importance, combined with similarity; warns "If the system over-extracts, this could lead to reduced precision... under-extracts... low recall"; collection memories must "reconcile new information with previous beliefs, either deleting/invalidating or updating". Design guidance only. — https://langchain-ai.github.io/langmem/concepts/ (downloaded copy)
- Anthropic memory tool docs: "Periodically delete memory files that haven't been accessed in a long time" (access-based expiry left to the app); prompt: "keep its content up-to-date, coherent and organized. You can rename or delete files that are no longer relevant." — https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool
- Claude Code auto memory docs: four memory types (user, feedback, project, reference); MEMORY.md index loads first 200 lines/25KB; Claude "decides what's worth remembering"; at the limit Claude Code reminds Claude to "merge or drop stale entries"; memory files are excluded from transcript retention sweep ("stay until you or Claude edits or deletes them"). Path-scoped rules exist for CLAUDE.md ("Longer files consume more context and reduce adherence"). — https://code.claude.com/docs/en/memory (downloaded copy)
- "Auto dream" (Claude Code, reported Mar 2026, unofficial/community-spotted, v2.1.83): background process that merges overlapping entries, removes outdated/conflicting information, replaces relative with absolute dates. Tessl article, secondary, says "isn't yet an official feature". — https://tessl.io (Tessl blog, Paul Sawers, 26 Mar 2026)
- Xiong et al. 2025 (arXiv 2505.16067, academic): history-based deletion (drop records retrieved >= n times with mean utility < threshold) and periodic deletion compared; "with a reliable utility evaluator, history-based deletion can improve agent performance"; results variable with weak evaluators. Only utility-feedback deletion has direct empirical support. — https://arxiv.org/html/2505.16067
- Memory-security survey (arXiv 2604.16548, Apr 2026) frames a lifecycle incl. "Forget & Rollback" and lists provenance visibility, principal-scoped retrieval, rollbackability as defenses. Survey, not evidence. — https://arxiv.org/html/2604.16548
- Time decay / TTL / explicit turn-task-session-project scopes with expiry as a mechanism for user constraints: I found NO evaluation in any source I read.

**Evidence that stale/over-general memories hurt**
- Xiong et al.: "experience-following" (similar input gives similar output); "if a retrieved memory record contains noisy or incorrect outputs, the agent is likely to replicate and even amplify these errors... If the resulting execution is then added back into memory, the error is likely to be further propagated". Also "misaligned experience replay". Add-all is not safe; future task feedback can serve as "free quality labels". — https://arxiv.org/html/2505.16067
- BenchPreS (arXiv 2603.16557, Mar 2026): "current LLMs treat preferences as globally enforceable rules rather than as context-dependent normative signals". Misapplication Rate up to 86.48% (Gemini 3 Pro, also highest appropriate-application 88.69%); GPT-5.2 best separation yet MR 40.95%; "Models with stronger preference adherence exhibit higher rates of over-application"; reasoning and selectivity prompting don't fix it. Most direct proxy for "literal-wording glue". — https://arxiv.org/html/2603.16557
- PersistBench (arXiv 2602.01146, Feb 2026): 18 LLMs; median failure rate 53% on cross-domain leakage, 97% on memory-induced sycophancy. Defensive prompting tested on 5 models (results not extracted here). — https://arxiv.org/html/2602.01146
- OP-Bench (arXiv 2601.13722, Jan 2026): over-personalization (Irrelevance, Repetition, Sycophancy) over 1,700 instances; agents "retrieve and over-attend to user memories even when unnecessary"; post-processing mitigations "provide only limited improvements and often reduce personalization performance". — https://arxiv.org/html/2601.13722
- STALE (arXiv 2605.06527, May 2026): 400 implicit-conflict scenarios, 1,200 queries, up to 150K tokens; best model only 55.2% overall; "systems often retrieve updated evidence but fail to act on it"; models "accept outdated assumptions embedded in a user's query". Prototype CUPMem does write-time state consolidation (numbers not extracted). — https://arxiv.org/html/2605.06527
- LongMemEval (Wu et al., arXiv 2410.10813, Oct 2024, background): includes knowledge-update and temporal-reasoning abilities; "commercial chat assistants and long-context LLMs showing a 30% accuracy drop" on sustained interactions. I did not extract per-system KU scores. — https://arxiv.org/html/2410.10813
- User complaints (anecdotal, OpenAI forum threads, via search; not opened): memory not updating, "Memory Updated" shown but not stored, outdated restored fragments, inferred context presented as fact. A vendor-adjacent blog argues tools "write facts down" but are "weaker at retiring them". [snippet-only] — https://community.openai.com/t/memory-not-updating-in-chatgpt-4o-issue-persists-across-conversations/1105721 ; https://memx.app/blog/when-ai-memory-goes-stale/
- No sourced complaint reports specifically about Cursor/Windsurf memories or Claude Code auto memory staleness were found; only the Tessl "auto dream" article (stale/conflicting notes motivate it).

**Poisoning and defenses**
- Compaction-Eviction Attack (Governance Decay): adversary biases compaction to delete a constraint; optimized injection raises violation 0% to 65% on a model immune to the fixed probe. — https://arxiv.org/html/2606.22528
- GhostWriter (arXiv 2607.06595, Jul 2026): ~98% injection, ~60% activation on personal agents; AM-Sentry = memory-saving policy + retrieval screen "dramatically reduces" success (no number extracted). — https://arxiv.org/html/2607.06595
- Defense-layer study (arXiv 2605.08442, May 2026): 29 endpoints; injection (storage) and execution are separable; "Anthropic's Opus and Sonnet models mostly do not store a forwarding directive"; of six defences only Memory Sandbox (removes recall tool) blocks, bypassed by some models rebuilding the instruction from retrieval. Prompt hardening gave no protection. — https://arxiv.org/html/2605.08442
- Memory-file prompt injection in Claude Code and Codex (arXiv 2607.14611, Jul 2026): hard to make an agent overwrite its own memory from untrusted content, but payloads already in memory files attack current and future sessions. — https://arxiv.org/html/2607.14611
- MPBench (arXiv 2606.04329): "existing prompt injection defenses fail to cover memory poisoning attacks". — https://arxiv.org/html/2606.04329
- Provenance defenses (SMSR HMAC tags, MemLineage, MemAudit) and a Jan 2026 EHR finding that Llama Guard/sanitization are largely ineffective vs MINJA: [snippet-only, unverified]. Original MINJA (arXiv 2503.03704, Mar 2025) downloaded but figures not extracted.
- Implication of "trust only user turns": Governance Decay shows even a pinned buffer is overridable by in-stream impersonation; user-turn-only extraction is consistent with that but untested.

**Instruction-count scaling**
- IFScale (arXiv 2507.11538, Jul 2025): 500 keyword instructions, 20 models; best frontier model 68% at 500 instructions; three decay shapes: threshold (reasoning models, near-perfect through "moderate densities (100-250)"), linear (gpt-4.1, claude-sonnet-4), exponential (gpt-4o, llama-4-scout); primacy bias (earlier instructions favored); errors shift from modification to omission under load. Caveat: keyword-inclusion task, not coding-agent constraints; 2025 models. Governance Decay's overload test (1 relevant + 15 distractors) gave 0% violation. Pins of a handful of items are well under measured degradation thresholds; no study of 20-50 coding-agent constraints. — https://arxiv.org/html/2507.11538

### Inferences
- Stickiness is an unmeasured gap in the constraint-registry literature: both papers optimize recall of constraints and define SC lifetime as "until revised, revoked, or its scope ends" without implementing it. Adjacent evidence (BenchPreS MR 40-86%, OP-Bench, PersistBench) shows models over-apply any stored user statement as a global rule, so verbatim re-injection plausibly worsens literalism; this is inference, not measured.
- The LiC extractor lacks scope, type, supersession and removal, so a "don't touch auth for now" would be appended permanently (dedup only). A design needs fields the papers lack (scope, expiry trigger, revoked-by, source turn) plus a user-turn revocation path distinct from the attack path Governance Decay tests.
- Dedup against the registry is the only conflict handling in LiC; STALE shows implicit supersession is hard (55.2% best), so lexical or explicit-only revocation will miss "okay, auth is fair game now".

### Gaps
- No study of false-positive rate of constraint extraction, task-scoped vs session-scoped constraints, or expiry of user instructions.
- No per-system LongMemEval knowledge-update numbers extracted; no independent evaluation of Graphiti invalidation or Mem0 DELETE correctness.
- Cursor/Windsurf memory complaints not found; Claude Code auto-memory staleness only via secondary article.
- MINJA/AgentPoison figures and 2026 provenance-defense papers not opened.

## B. Who should write memory

### Takeaway
The writer-type comparison is argued from design tradeoffs and vendor docs; I found no controlled study comparing hot-path agent writing vs sidecar vs per-turn extraction vs compaction summarizer on downstream task success. The closest measurements are extraction recall (LiC: 93% for a 9B extractor vs 28-38% for compaction prompts), sleep-time compute (different problem), and ACE/DC context-update ablations. User confirmation friction vs accuracy is unmeasured.

### Cited Findings
- Compaction summarizer as writer: LiC finds LLM compactors drop most side constraints; non-LLM compactors "retain essentially no SCs of any type"; best SC-targeted prompt 37.6% on WildChat vs per-turn extractor 90.3% (52.7 points higher). Governance Decay: dropped constraint = 38% violation vs 0% when kept; compaction "treats standing policies as low-salience content". Both are author-designed benchmarks with injected constraints (SWE-Natural is the natural-data exception, where compactors reach at most 28.6%). — https://arxiv.org/html/2608.11242 , https://arxiv.org/html/2606.22528
- Per-turn small-model extraction (LiC, Mem0): Qwen3.5-9B per-turn extractor with registry for dedup, 93.0% avg retention, no precision reported. Mem0 extracts per message pair using summary plus recent messages and then an LLM chooses ADD/UPDATE/DELETE/NOOP (vendor evaluation on LOCOMO). Governance Decay's own limitation: implicit constraints out of scope. LangMem docs name the over- vs under-extraction tradeoff. — https://arxiv.org/html/2608.11242 , https://arxiv.org/html/2504.19413 , LangMem concepts page
- Hot path vs background (LangMem docs): active/"conscious" formation "is easy to implement and lets the agent itself choose... However, it adds perceptible latency to user interactions, and it adds one more obstacle to the agent's ability to satisfy the user's needs"; background/"subconscious" formation is "perfect for ensuring higher recall of extracted information" and avoids tool-choice complexity but updates are delayed. Vendor design statement, no measurements. — https://langchain-ai.github.io/langmem/concepts/
- Letta sleep-time compute (Lin et al., arXiv 2504.13171, Apr 2025): offline "thinking" about context reduces test-time compute for equal accuracy by about 5x on Stateful GSM-Symbolic and AIME; scaling it adds up to 13% / 18% accuracy; amortizes across multi-query contexts. This tests pre-computed inference over a context, not memory-write quality, and the sidecar is not shown to beat the main agent at note-taking. — https://arxiv.org/html/2504.13171
- Anthropic memory tool: main-agent-authored; auto-injected prompt "ASSUME INTERRUPTION: Your context window might be reset at any moment, so you risk losing any progress that is not recorded in your memory directory" and "record status / progress / thoughts"; "Claude usually refuses to write sensitive information"; app should validate and expire. Claude Code auto memory: model-written notes during work, skips derivable info; "doesn't save something every session". No measurement of miss rate. — memory tool docs and https://code.claude.com/docs/en/memory
- Auto dream (reported Mar 2026): background consolidator over memory files, only memory files, runs after usage/time thresholds; shows Anthropic splitting hot-path writes from a sidecar curator, motivated by "stale details, contradictions, and noise". Secondary reporting, unofficial. — Tessl article above
- ACE (arXiv 2510.04618, Oct 2025; Stanford/SambaNova authors): Generator / Reflector / Curator split "Inspired by... Dynamic Cheatsheet"; incremental delta updates counter "brevity bias" and "context collapse" (monolithic LLM rewriting "degrade[s] into shorter, less informative summaries over time"); +10.6% agents, +8.6% finance. Relevant: rewrite-whole-memory writers (like summarizers) lose detail; append/delta curation did better. Benchmarks are AppWorld/finance, not user constraints. — https://arxiv.org/html/2510.04618
- Dynamic Cheatsheet (arXiv 2504.07952, Apr 2025): the model itself curates a cheatsheet at test time; GPT-4o Game of 24 10% to 99%; Claude 3.5 Sonnet AIME 2024 +27%. Self-authored memory, worked best when it stored reusable code, not user constraints. — https://arxiv.org/html/2504.07952
- Writer errors and poisoning: Xiong et al. show write-all is harmful and write quality gating via evaluator helps; GhostWriter shows agent-self-written memory can be poisoned by hidden payloads (98% injection), mitigated by a memory-saving policy; Claude Code memory-file study finds overwriting memory from untrusted content is hard but planted payloads persist. Argues for writer provenance (user turns trusted, tool output not). — https://arxiv.org/html/2505.16067 , https://arxiv.org/html/2607.06595 , https://arxiv.org/html/2607.14611
- ChatGPT memory design: I could not read OpenAI's memory FAQ (fetch empty). A secondary analysis [snippet-only, unverified] cites 2,050 memory records from 80 ChatGPT users, 96% proactively created by the system, and argues low approval rates conflate UI friction with low-value extraction — https://yage.ai/share/ai-memory-benchmark-precision-en-20260719.html
- User confirmation: search found no controlled friction-vs-accuracy study. Commentary favors tiered gating (auto-write explicit user preferences and tool outputs, consolidate model reflections); an ACL 2026 workshop paper proposes a Memory-Clarification Boundary benchmark (persist / ephemeral / verify / clarify) [snippet-only]. — https://aclanthology.org/2026.nora-1.2.pdf ; https://urandom.io/blog/2026-04-12-agent-memory-is-a-write-path-problem

### Inferences
- For constraints specifically, the strongest measured result is that a dedicated per-turn extractor reading raw user messages beats compaction-time summarization on recall (93% vs <=38%, same benchmark family). This does not show it beats agent-authored notes; that comparison was not run in any source found.
- Main-agent hot-path writing is least likely to capture constraints in time under context pressure (docs admit added "obstacle"; Anthropic's prompt presumes interruption), but no miss rates were found.
- Per-turn extraction sees the user turn but not task state, so it cannot know whether "for now" applies to this sub-task; scope judgment probably needs the main agent or a sidecar with task context. Design opinion, unmeasured.
- Quality-gating (Xiong) and delta updates (ACE) are the evidence-backed ways to prevent bad writes from compounding.

### Gaps
- No head-to-head writer-type evaluation; no measurement of sidecar/main-agent write races; no extraction precision for user constraints; no friction-vs-accuracy data on confirmation. Letta docs, OpenAI memory documentation and Mem0's extraction prompt contents not read.
